Getting Started

What this is

A runnable, empty Unity project built on Sorolla Core. Clone it, and you already have a booting app with a home menu, a Play → Win/Lose → End-panel loop, and every Core system (UI, persistence, live-ops, monetization, profile, tournaments) wired from the first frame. You add your gameplay; you don't build the plumbing.

The project splits cleanly into two layers. Sorolla Core (Assets/Sorolla Core/, namespace Sorolla) is the reusable framework and never references game code. The template app (Assets/_Template/, namespace Template) is the thin, game-agnostic shell that boots Core and stands in for a real game — it is the layer you edit and eventually replace with your own.

Two layers, two namespaces

Framework code lives in the Sorolla.Core assembly (root namespace Sorolla). Everything under Assets/_Template/ is the app layer (namespace Template) — the part you make yours.

What boots ready

From the moment you press Play, the shell brings up the entire Core stack — not a stub. The Init scene hosts a GameManager whose _gameManagers[] array holds eight Core services, initialized in dependency order:

  1. PlayerProfileService — local identity (name, flag, avatar)
  2. TournamentService — weekly client-side trophy ranking
  3. LivesManager — regenerating lives / energy
  4. EventManager — live-ops event framework
  5. CurrencyService — soft/hard currency wallet
  6. PowerUpService — power-up / booster inventory
  7. EntitlementService — durable entitlements (no-ads, etc.)
  8. PurchasingService — IAP with a mock backend in the editor

Plus UIManager, AudioManager, TutorialController, the SaveSystem, and the Core LevelFlowManager. TemplateGameManager additionally registers an IIconResolver and an ISkinService. Every one of these is resolvable from the ServiceLocator before any Game-scene Start() runs.

Wiring, not building

The value of the template is that this machinery is already assembled and load-order-correct. You wire your game onto it through interfaces — you never re-derive the boot sequence.

The three scenes

The app boots through three scenes in build order — PreInit (0) → Init (1) → Game (2), all under Assets/_Game/Scenes/. They are covered in detail under The Template › 3-scene boot.

Configs are inert

The ScriptableObjects in _Template/Data/ exist and are wired, but hold placeholder/empty data. Filling them with your content is one of the first steps in Building Your Game.

The Template

3-scene boot

The app initializes across three additive scenes so the loading screen, service init, and gameplay each own a clean stage. Build order: PreInit = 0, Init = 1, Game = 2.

PreInit — show something instantly

A Camera, a Canvas with a full-screen LoadingScreen image, and Sorolla.PreInitLoader (fields _initSceneName = "Init", _loadingScreen). Its Start() loads Init additively; when init completes it hides the loading screen and unloads itself.

PreInitLoader.Start()
  → SceneManager.LoadSceneAsync("Init", Additive)
// …later, once Init finishes booting:
PreInitLoader.OnInitializationComplete()
  → hide loading screen → unload PreInit

Init — bring up the framework

Two GameObjects drive it:

  • Initializer → Sorolla.GameInitializer (_gameSceneName = "Game", _consentTimeoutSeconds = 10f).
  • GameManager → Template.TemplateGameManager, with all non-MonoSingleton managers and the EventSystem parented as its children (see the persistence rule).
GameInitializer.Start()
  → GameManager.Instance.InitializeAsync()          // SaveSystem, LevelFlow, Audio,
  →                                                 //   Tutorial, then each _gameManagers[]
  → SceneLoader.LoadSceneAdditiveAsync("Game")
  → SetActiveScene(Game)
  → GameInitializer.OnSceneLoaded (static, awaited)  // Game-scene systems hook here
  → WaitForConsentAsync()                            // up to 10s Palette consent gate
  → PreInitLoader.Instance.OnInitializationComplete()
  → unload Init

Game — your playground

A bare Camera + Light, the LevelSessionController (drives the play loop), TemplatePlaceholderGameplay with its WIN/LOSE overlay canvas, and the tournament host. This is the scene you populate with real gameplay.

One EventSystem, one AudioListener

The persistent set (under GameManager) owns the single EventSystem; the Game camera owns the single AudioListener. Adding a second of either produces Unity warnings — keep exactly one of each.

TemplateGameManager runtime

The single place a new game starts customizing service registration. It subclasses Core's GameManager and adds the two wirings the base can't do generically.

public class TemplateGameManager : GameManager
{
    [SerializeField] private TemplateIconResolver _iconResolver;
    [SerializeField] private SkinCatalog _skinCatalog;

    protected override void Init()
    {
        base.Init();               // Core registers UI, audio, tutorial + each _gameManagers[]
        RegisterIconResolver();    // ServiceLocator.Register<IIconResolver>(_iconResolver)
        RegisterSkinService();     // builds a SkinService from _skinCatalog, persists to "cosmetics"
    }
}

MonoBehaviour services are wired through the base _gameManagers[] array in the Init scene (in dependency order). Non-MonoBehaviour services — like ISkinService, built from a SkinCatalog and backed by SaveSystem.Load/Save<KVSaveData>("cosmetics") — are registered in code here, after base.Init().

Your first edit

When you build a real game, TemplateGameManager (or a subclass of it) is where you register your services. Mirror the IconResolver/SkinService pattern for non-MonoBehaviour services, and add MonoBehaviour services to _gameManagers[] in the scene.

Manager persistence rule

⚠️ Managers must be children of GameManager

MonoSingleton.Awake() calls DontDestroyOnLoad(transform.root). Only UIManager and GameManager are MonoSingletons, so only they persist on their own. Every other manager is a plain SorollaManager (a MonoBehaviour) and must be a child of the GameManager GameObject — so DontDestroyOnLoad carries it through the Init-scene unload. A manager left at the scene root is destroyed when Init unloads, and its ServiceLocator registration silently becomes a fake-null reference.

This was a real bug during the shell's construction: managers registered fine, then vanished on the Init→Game transition. The fix was to reparent every non-MonoSingleton manager under GameManager. When you add your own managers, parent their GameObjects under GameManager too.

Play loop — LevelSessionController runtime

Orchestrates the whole session: MainMenu → Gameplay → EndPanel → MainMenu. It lives in the Game scene and is used as-is; games extend it for custom behavior.

protected virtual async void Start()
{
    await UniTask.Yield();                        // let level systems subscribe first
    _levelFlow = ServiceLocator.Instance.Resolve<ILevelFlowManager>();
    _levelFlow.OnEndPanelDismissed += HandleEndPanelDismissed;
    await ShowMainMenuAsync();                     // Push UIScreenId.MainMenu, clearStack
}

public virtual void RequestStartLevel()           // ← the Play button calls this
{
    // hide the top screen → ShowGameUI(true) → StartLevel(CurrentLevelIndex)
}

// win/lose auto-opens the end panel; dismissing it returns to the menu:
private void HandleEndPanelDismissed() => _ = ShowMainMenuAsync();

Overridable hooks: GetMainMenuScreenId() (defaults to UIScreenId.MainMenu), OnMainMenuShown(), and OnLevelStarting(int). The loop closes itself: on win/lose the flow manager auto-shows the end panel, and dismissing it calls ShowMainMenuAsync again.

Register the end panels or the loop stalls

Win auto-opens UIPanelId.LevelComplete; lose auto-opens UIPanelId.GameOver. If those ids aren't registered in the UIRegistry, OpenPanelAsync returns null and the session never returns to the menu.

Built-in features: Profile & Tournament

The shell wires two Core features end-to-end as worked examples of how a menu surfaces a system.

Profile

PlayerProfileService boots in _gameManagers[] and exposes local identity through IPlayerProfile. The menu's Profile button opens UIPanelId.Profile; the panel edits name, country flag, and avatar (sourced from ProfileCatalog), persisted to the profile save file.

Tournament

TournamentService runs a weekly, client-side trophy ranking against deterministic bots. Because TournamentScreen is a plain activation-driven MonoBehaviour (it rebuilds in OnEnable), it is not pushed through the screen stack — TemplateTournamentHost just toggles it active. Standings are seeded from TournamentConfig and persisted to the tournament save file.

Activation-driven, not stack-driven

Treat TournamentScreen as a special case: toggle it with SetActive (via the host), never PushScreenAsync. Your own screens should generally go through the UIManager stack instead.

Core Reference

Core Principles

1 — Agnostic design

Sorolla Core never references game-specific code. All game functionality is reached through:

  • Interfaces defined in Core (e.g. IGameplayUI, IPlayerProfile, ILevelFlowManager)
  • ServiceLocator for runtime dependency resolution
  • Events for decoupled communication

2 — Interface-based coupling

Your game implements Core interfaces and registers them via ServiceLocator:

// Game registers its implementations
ServiceLocator.Instance.Register<IGameplayUI>(myLevelUI);
ServiceLocator.Instance.Register<ILevelFlowManager>(myLevelManager);

// Core resolves them at runtime
var gameplayUI = ServiceLocator.Instance.TryResolve<IGameplayUI>();
gameplayUI?.ShowGameplayUI(true);

3 — Extensible enums

UI and reason enum values are partitioned so games extend without editing Core:

  • 0–99 — reserved for Sorolla Core (generic screens/panels/reasons)
  • 100+ — available for game-specific values

ServiceLocator

The single dependency-resolution mechanism. Game systems register implementations; anyone resolves them by interface or concrete type.

// Register
ServiceLocator.Instance.Register<ILevelFlowManager>(adapter);

// Resolve (hard — logs an error if missing)
var flow = ServiceLocator.Instance.Resolve<ILevelFlowManager>();

// Resolve (soft — returns null if missing)
var ui = ServiceLocator.Instance.TryResolve<IGameplayUI>();
Registration timing

Resolve a service only after it has been registered. Register everything synchronously up front (in Init() / the boot pass) so anything resolved during a scene's Start() is already available. Registering inside an async init pass can let early resolvers get a null.

Async init

Managers needing asynchronous setup (remote config, IAP catalog, live config) implement IAsyncInitializable and are awaited by GameManager; the rest use the synchronous SorollaManager.Init(). Boot order is set by the _gameManagers[] array — list dependencies before their consumers.

UI System runtime

Central screen/panel management with async open/close. Screens and panels are registered in a ScriptableObject UIRegistry and addressed by enum id. Each instance is cached once — closing means SetActive(false), never Destroy, so Awake listeners never accumulate.

// Screens (full-screen, stacked)
await UIManager.Instance.PushScreenAsync(UIScreenId.MainMenu, args, clearStack: true);
await UIManager.Instance.PopScreenAsync();
var top = UIManager.Instance.GetTopScreen();

// Panels (overlays)
await UIManager.Instance.OpenPanelAsync(UIPanelId.ConfirmDialog, args);
await UIManager.Instance.ClosePanelAsync(panelInstance);

Object Pooling

Two layers work together:

  • Pool + PoolManager — the underlying pool data structure and a static registry of named pools.
  • FXPoolService — a convenience singleton for VFX/particle pooling.
FXPoolService.Instance.EnsurePool(poolId, prefab);
var ps = FXPoolService.Instance.GetPooledComponent<ParticleSystem>(poolId);
When to pool

Pool anything instantiated frequently — VFX, projectiles, floating numbers — to avoid per-spawn GC. iOS is especially sensitive to allocation spikes.

Persistence & Analytics runtime

The single save story. JSON files written atomically to Application.persistentDataPath; each system owns its own file.

TypeRole
SaveSystemStatic API: Save(data, file) / Load<T>(file) (and async variants). Newtonsoft-based with hardened settings.
LocalFileStorageAtomic write via temp file + serialized rename.
BackupManager / SaveValidatorTimestamped backups; JSON sanity check before deserialize.
One file, one writer, synchronously

Each system owns its save file and persists at discrete points. Do not fan out concurrent async saves to the same file — overlapping writes on the shared temp file corrupt or lose data. iOS is especially sensitive to per-frame disk I/O; batch saves at level end or behind dirty flags.

Key-value routing

The persistence adapter routes KV keys to save files by prefix, so subsystems share storage without name collisions (e.g. the events file is owned by EventManager; generic live-ops KV uses its own bucket; the template's cosmetics use cosmetics).

Analytics fan out through Palette.* only — no vendor SDK is referenced from game or Core modules.

Live Config optional

Push balance tweaks from a Google Sheet to every installed build on the next cold boot — without shipping a new binary.

Two layers

  1. Content registry (SOs, ship with the build) — prefabs, sprites, VFX refs. Can't live in JSON; change only with a new binary.
  2. Tunables (JSON, live-updatable) — HP, damage, prices, magnitudes. Authored in SOs, serialized to JSON for transport.

Fallback chain (runtime)

On cold boot LiveConfigBootstrapper tries each in order: 1) fetch the Apps Script URL (8s timeout) → 2) persistent cache from the last good fetch → 3) baked StreamingAssets/live_config.json. A fresh install with no internet still boots with valid data.

The step that bites people

When adding a new live field/category, the server-side Apps Script must mirror the C# shape or the fetched JSON won't match the client. Redeploy via Manage deployments → Edit → New version to keep the URL stable, and clear the Apps Script cache so the 6h TTL doesn't delay propagation.

Building Your Game

Building your game — walkthrough

A hands-on path from the empty shell to your first playable level. Each step is small and edits as little as possible; the plumbing already works.

1 — Clone & rename

Clone the template repo and set your product name and bundle id in Project Settings → Player. Nothing else needs renaming to start.

2 — Register your services

Edit TemplateGameManager (or subclass it). Add your MonoBehaviour SorollaManager services to the scene GameManager's _gameManagers[] array in dependency order, and register non-MonoBehaviour services in the Init() override after base.Init() — mirror the IconResolver / SkinService pattern.

protected override void Init()
{
    base.Init();
    ServiceLocator.Instance.Register<IMyService>(new MyService(...));
}
Persistence rule

Any new manager GameObject must be parented under GameManager, or it's destroyed when Init unloads. See Manager persistence rule.

3 — Fill the inert configs

Populate Assets/_Template/Data/ with your data: ProfileCatalog (avatars/flags), TournamentConfig (tiers/bots), PurchasingCatalog (products), PowerUpRegistry, SkinCatalog, and the AudioLibrary. DataSheet makes this quick.

4 — Populate the Game scene

Add your gameplay objects (board, characters, camera rig) to Game.unity. Keep LevelSessionController — it drives the menu/loop.

5 — Wire gameplay to the level flow

Build level content when the flow asks, and report outcomes back to it:

var flow = ServiceLocator.Instance.Resolve<ILevelFlowManager>();
flow.OnLevelSetupRequested += level => BuildLevel(level);   // build/reset content
// …from your gameplay:
flow.WinLevel();                        // defaults to AllGoalsComplete
flow.LoseLevel(LevelEndReason.TimeUp);  // or your own reason (100+)
Delete the placeholder

Once your gameplay drives win/lose, delete TemplatePlaceholderGameplay and its WIN/LOSE overlay canvas from the Game scene — it exists only to make the empty shell clickable.

6 — Style the menu & end panels

The MainMenu, LevelComplete, and GameOver prefabs are functional but plain. Restyle their art and layout — the logic (MainMenuScreen, TemplateEndPanel) is already wired, so this is visuals only.

7 — Add your own screen or panel

  1. Subclass UIScreen or UIPanel.
  2. Build a prefab (root = RectTransform + your component).
  3. Add a game enum id (≥100) to UIScreenId/UIPanelId (extensible-enums principle).
  4. Register the prefab in UIRegistry.
  5. Open via UIManager.PushScreenAsync / OpenPanelAsync.

8 — Remote-config-tunable values

For values you want to balance without a rebuild, add a key and read it via RemoteConfig.Get* (see Live Config for the manifest/publish workflow and the fallback chain).

Checklist & gotchas

Manager persistence

Every non-MonoSingleton manager must be a child of GameManager, or it dies on the Init-scene unload and its registration goes fake-null.

Register the end panels

LevelComplete (4) and GameOver (5) must be in the UIRegistry, or win/lose can't open a panel and the loop stalls.

Exactly one EventSystem & one AudioListener

EventSystem lives in the persistent set (under GameManager); the AudioListener lives on the Game camera. Don't add a second of either.

TournamentScreen is activation-driven

Toggle it with SetActive via TemplateTournamentHost, not PushScreenAsync.

DOTween asmdef

Keep DOTween's createASMDEF: 1 setting — regenerating without it deletes DOTween.Modules.asmdef and breaks the compile.

Verifying a clean compile

The template Core compiles clean. In-editor, check_compile_errors is authoritative — the logs buffer can hold stale errors from before a recompile.
